## US-001

# US-001 — Start the whole stack with one Docker Compose command

Epic: Infrastructure and application foundation
Priority: P0
Status: Done
Evidence: 2026-11-01: `docker compose up -d --build` → postgres/redis healthy, migrate Exited (0), web healthy, worker up; postgres and redis publish no host port; missing POSTGRES_PASSWORD/APP_SECRET refused at `compose config`; users 2 → 2 across down/up; web unhealthy when postgres stopped and healthy again on restart; worker restarted by Compose after SIGTERM; E2E 42/42 against the stack
Planned sprint: 1 · Dependency wave: 0

## User Story

As a developer or operator,
I want to start Banyan with `docker compose up -d --build`,
so that every environment is reproducible and the MVP can be released from one artefact.

## Business Context

The repository has a single Dockerfile and no Compose file. The brief's release criteria require the full application to start under Docker Compose.

## Functional Requirements

- Compose services: web (Next.js UI + API), worker, postgres, redis
- Named volume for Postgres data that survives `docker compose down`
- Internal network; only web publishes a host port
- Health checks on every service; web depends on healthy postgres and redis
- Restart policy `unless-stopped`

## Non-Functional Requirements

- Security: no secrets in the Compose file; all from .env
- Reliability: services restart on failure; graceful shutdown on SIGTERM
- Performance: cold start under 90 s on a developer laptop

## Acceptance Criteria

- Given a clean checkout and a filled .env,
  When I run `docker compose up -d --build`,
  Then `docker compose ps` shows web, worker, postgres and redis as healthy
- Given the stack is running,
  When I run `docker compose down` and `up -d` again,
  Then my workspace data is still there
- Given postgres is not yet healthy,
  When web starts,
  Then web waits instead of crashing

## Dependencies

- Internal story dependencies: none (optional: [US-002](USER_STORIES.md#us-002))
- External services: none
- Infrastructure dependencies: Docker Engine 24+, Docker Compose v2
- API dependencies: none

## Technical Implementation

- Frontend changes: None
- Backend changes: None
- Database changes: Postgres 16 service with named volume `banyan-pgdata`
- Integration changes: None
- Background processing changes: worker service runs the queue consumer (US-006)

## Test Scenarios

- Happy path: compose up, all services healthy, GET /api/health returns ok
- Validation failure: missing APP_SECRET in .env makes web exit with a clear message
- Authorization failure: postgres and redis ports not reachable from the host
- External service failure: stop postgres: web health turns unhealthy, recovers when postgres returns
- Retry and recovery: kill worker: Compose restarts it

## Definition of Done

- [x] Unit tests pass
- [x] Integration tests pass

## US-005

# US-005 — Durable job queue on Redis

Epic: Infrastructure and application foundation
Priority: P0
Status: Done
Evidence: 2026-11-01: BullMQ queue (src/lib/queue); 19 unit tests (payload validation, deterministic job ids, dead-letter retention, fails loudly without Redis); live: delayed job held in Redis and processed after a worker restart
Planned sprint: 1 · Dependency wave: 0

## User Story

As a the platform,
I want to enqueue background work durably,
so that slow or external operations never block a request and survive restarts.

## Business Context

Background work today is triggered by an HTTP tick every 60 s (TD-02). The brief requires Redis-backed background jobs (ADR-002).

## Functional Requirements

- Queue module: enqueue(job, payload, {delay, attempts, backoff}), consume(handler)
- Jobs survive a worker restart
- Failed jobs move to a dead-letter set after max attempts
- Job ids are deterministic where the operation is idempotent

## Non-Functional Requirements

- Reliability: at-least-once delivery; handlers must be idempotent (enforced by Postgres unique keys)
- Security: Redis not exposed outside the Compose network

## Acceptance Criteria

- Given a job is enqueued,
  When the worker restarts before processing it,
  Then it is processed after the restart
- Given a job fails three times,
  When the max attempts is reached,
  Then it is in the dead-letter set with its last error
- Given the same idempotent job is enqueued twice,
  When processed,
  Then the side effect happens once

## Dependencies

- Internal story dependencies: [US-001](USER_STORIES.md#us-001)
- External services: none
- Infrastructure dependencies: Redis 7
- API dependencies: none

## Technical Implementation

- Frontend changes: None
- Backend changes: src/lib/queue/ (client, enqueue, consumer, dead-letter)
- Database changes: None
- Integration changes: None
- Background processing changes: Defines the queue all other jobs use

## Test Scenarios

- Happy path: enqueue → processed
- Validation failure: unknown job type rejected at enqueue
- Authorization failure: n/a
- External service failure: Redis down: enqueue fails loudly, request returns 503
- Retry and recovery: handler throws twice then succeeds; processed once
